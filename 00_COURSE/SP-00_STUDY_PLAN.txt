Abstract--This plan sets out how the author will study, record, and
critically review a mathematics course taught as a sequence of
projects, the first of which is the Lean 4 theorem prover and
programming language. It fixes a notebook organized by project and by
date; a plain-ASCII, IEEE-style session report whose final section is
a critical review against a register of best practices; a convention
under which tables and figures are separate files, cited the way one
cites a picture or a data source; and an editorial policy for
documenting discussions and chat histories. Because the class spends
most of its time on what the material means, the plan also gives a
protocol and an opening agenda for those discussions. Each discussion
is tied to a concrete Lean artifact and read through an electrical
engineer's lens of specification, verification, and trust.

Index Terms--Lean 4, interactive theorem proving, propositions as
types, formal verification, verification and validation, engineering
notebook, IEEE style.

III. NOTEBOOK METHOD
------------------------------------------------------------------------

A. Folder Structure

The notebook is organized by project and by date, as shown in Fig. 1
[file: 00_COURSE/fig/SP-00-F01_FOLDER_TREE.txt]. Material that applies
to every project lives in 00_COURSE. Blank forms live in 01_TEMPLATES.
Each project has one folder (P01_LEAN, then P02_..., and so on)
holding a project index, a Lean workspace where one is needed, and one
sub-folder per session date in ISO 8601 form, YYYY-MM-DD, which sorts
in date order in any file listing. A date folder holds that day's
report, chat logs, and the figures (fig/) and tables (tab/) that the
report cites. Third-party material is kept in 99_LOCAL, which is not
published (Section III-I).

No IEEE standard prescribes the layout of a personal notebook. "IEEE
storage format" is interpreted here as IEEE editorial conventions for
the documents themselves [17], combined with the practice of uniquely
identified, self-describing information items [14]. This
interpretation is to be confirmed (A-04).

B. Document Identifiers and File Names

Every file carries a Document ID in its header and in its file name,
so that a file copied out of its folder still identifies itself. The
scheme is given in TABLE I
[file: 00_COURSE/tab/SP-00-T01_DOCUMENT_IDS.txt].

File names use only the characters A-Z, a-z, 0-9, hyphen, underscore,
and period, and never spaces. The form is

    <Document ID>[_<SHORT_TITLE>].txt

for example P01-2026-11-25-R.txt or SP-00-F01_FOLDER_TREE.txt.

C. Text Format

1) Character set: 7-bit ASCII only. No tabs, curly quotes, special
dashes, or symbols. A dash is written "--". Mathematical and Lean
symbols are written as described in Section III-H.

2) Line length: a hard line return at or before column 72, so that a
file reads the same in any editor, terminal, printout, or diff.

3) Headings: IEEE order and numbering. Sections take capital Roman
numerals and capital letters (I. INTRODUCTION); subsections take
capital letters (A. Purpose); third-level headings are numbered
in-line (1) Character set:). Cross-references take the form
"Section III-C".

4) Emphasis: no typographic emphasis. A term at its point of
definition may be marked with asterisks, *like this*, sparingly.

5) Equations: on their own line, indented, and numbered at the right
margin, so that they can be cited as (1), (2), and so on.

        a + 0 = a                                              (1)

D. Figures and Tables as Cited Artifacts

Tables and figures are never embedded in the body text. Each is its
own file in the fig/ or tab/ folder beside the document that cites
it, and the body cites it the way one cites a photograph or a data
source: by its IEEE label and its file path, for example
"TABLE III [file: 00_COURSE/tab/SP-00-T03_P01_PHASES.txt]". This keeps
the prose readable at 72 columns, lets a table be corrected without
reissuing the report, and lets one table serve several reports.

IEEE labeling is kept. Figures are numbered in Arabic numerals, with
the caption below the figure ("Fig. 1."). Tables are numbered in
Roman numerals, with the label and a capitalized title above the
table ("TABLE I"). File names use two-digit indices (F01, T01) so
that they sort correctly; TABLE I is file T01.

A figure that is a binary image -- a photograph of the board, a
screenshot of the Lean infoview -- is stored beside an ASCII
descriptor file with the same Document ID and a different extension.
The descriptor gives the caption, the source, and a text description
of what the image shows. Templates: 01_TEMPLATES/TPL_FIGURE.txt and
01_TEMPLATES/TPL_TABLE.txt.

E. Citations

1) External sources: IEEE numeric style [17]. Within a document,
references are numbered [1], [2], ... in order of first citation and
listed at the end. The master register, 00_COURSE/REFERENCES.txt,
gives each source a permanent key (for example, TPIL4) so that it is
formatted once and renumbered in each document. Figure and table
files cite by key, e.g. [TPIL4], because one such file may serve
several documents that number their references differently.

2) Internal records (prior work in this notebook): cited by Document
ID in brackets, e.g. [P01-2026-11-25-C], and listed under "Internal
Records" after the external references.

3) Points within a record: cited by stable identifiers only --
section (Sec. V-B), chat turn (#003), best practice (BP-04), open
question (P01-OQ-03), or action (A-02) -- and never by page or line
number, which change when a file is edited. Example:
[P01-2026-11-25-C, #001].

F. Discussion and Chat Records

Every discussion that informs the notes -- in class, with peers, or
with an AI assistant -- is documented as a chat log,
Pnn-YYYY-MM-DD-C. A second discussion on the same date is -C2, and so
on. Two copies are kept.

1) RAW copy (Pnn-YYYY-MM-DD-C-RAW.txt): the transcript as captured,
never edited after capture. It is the record of provenance.

2) EDITED copy (Pnn-YYYY-MM-DD-C.txt): the copy that reports cite,
prepared under these rules.

  a) Spelling and grammar are corrected silently.
  b) Wording is tightened so that the exchange stays coherent and on
     the point. Meaning is never changed. Where the meaning is
     uncertain, the original wording is kept and marked [?].
  c) Editor insertions are in [square brackets]. Omitted material is
     marked [...], with a short reason for any omission longer than
     one sentence.
  d) Lean code, mathematical statements, error messages, and
     quotations from sources are copied verbatim and never
     "corrected", even when wrong -- the error may be the point.
  e) Turns are numbered #001, #002, ... with the speaker's role:
     STUDENT, PROF, PEER-n, or AI (with tool and model name). Peers
     are identified by role, not by name, unless they agree
     otherwise.
  f) The log closes with a summary: the key claims with their turn
     numbers, and any questions sent to the open-question register.

Template: 01_TEMPLATES/TPL_CHAT_LOG.txt. The first log is
[P01-2026-11-25-C].

G. Revisions

Once its date has passed, a document is changed only by issuing a new
revision letter (A, B, C, ...) with an entry in its revision history
saying what changed and why. An error found later is recorded as an
erratum in the critical review of the session in which it was found,
and corrected by revision of the original document, so that the
history of the mistake is kept [15], [16]. The notebook is a git
repository, published by "make deploy" as defined in DEC-00, rule
R-09; plain ASCII at 72 columns gives clean line-by-line differences.

H. Lean Source Files and Notation

1) Workspace: one Lake workspace per project, in P01_LEAN/lean/,
created with Mathlib as a dependency by following the current
community instructions [18]. Each session report records the
toolchain (the contents of the lean-toolchain file) and the Mathlib
version, as one records the model and calibration date of an
instrument (BP-04).

2) File names: Lean module names are derived from file names and
cannot contain hyphens, so a session source file is named
S<YYYYMMDD>_<nn>.lean -- for example, S20261125_01.lean -- and is
cited by its Document ID, P01-2026-11-25-S01.

3) Notation: .lean files are exempt from the ASCII rule and follow
the Mathlib style guidelines [19], which use Unicode. In the ASCII
notes, Lean is written with its ASCII alternatives where they exist
(-> for the arrow, forall, /\, \/) and otherwise with the editor
input code (\in, \<, \>), which is itself ASCII and is exactly what
one types in the editor. The correspondence is given in TABLE II
[file: 00_COURSE/tab/SP-00-T02_LEAN_ASCII_NOTATION.txt].

4) Completion: a result is recorded as proved only when its file
compiles with no sorry, and #print axioms on it does not list sorryAx
(BP-05).

I. Lecture Timestamps, Screenshots, and Third-Party Material

1) Timestamps: a moment in a lecture is cited as [Lnn @ h:mm:ss],
with its share link, https://youtu.be/<video id>?t=<seconds>, at
first use in a document. Lecture numbers and video identifiers are in
P01-SYL, TABLE I. A timestamp given without its link is not recorded
until the link is supplied (DEC-00, R-03).

2) Lecture frames: a frame is captured from the local video file at
the cited second by "make shot V=<video id> T=<seconds>" and stored
as 99_LOCAL/frames/<video id>_t<seconds>.png. The published figure
file holds a transcription of the frame, an analysis, and the command
that regenerates it (BP-15).

3) The author's own screenshots -- the editor, the Lean infoview --
are the author's material and are stored beside their figure file, as
in Section III-D.

4) Third-party material: full transcripts, video frames, and slides
stay in 99_LOCAL/, which .gitignore excludes from publication. Notes
quote short passages and cite them (BP-16; DEC-00, R-10).

IV. SESSION REPORT
------------------------------------------------------------------------

Each class session produces one report, Pnn-YYYY-MM-DD-R, written
within 24 hours from the raw notes and the edited chat log. Its form
is fixed by 01_TEMPLATES/TPL_SESSION_REPORT.txt and is outlined here.

    Header      Document ID, date, session, declaration, chat
                record, sources, toolchain
    Abstract    Three to five sentences; Index Terms
    I.          INTRODUCTION -- context; link to the previous report
    II.         PRIOR WORK -- earlier records and literature used
    III.        MATERIAL PRESENTED -- definitions, statements,
                worked examples
    IV.         RESULTS -- what was proved or shown; Lean status
    V.          DISCUSSION -- the philosophical discussion, written
                under the protocol of Section V-D
    VI.         CONCLUSION
    VII.        CRITICAL REVIEW AND BEST PRACTICES -- Section VI
    References  External [n], then Internal Records
    Figures and Tables -- label, caption, file path
    Revision History

Section V of a report is expected to be its longest, because that is
where class time is spent. For a short or exercise-only session a
short form is allowed: Sections II and III may be one paragraph each.
Section VII is never omitted.

V. STUDY METHOD FOR PROJECT P01: LEAN
------------------------------------------------------------------------

A. Objectives

By the close of P01 the author should be able to:

1) install, configure, and record a reproducible Lean 4 and Mathlib
   environment;
2) read and write proofs in both term style and tactic style, and
   explain how the two correspond;
3) state and prove results in propositional and first-order logic,
   with equality and with induction on the natural numbers;
4) find and use Mathlib results by name and by search, and name new
   results by the Mathlib conventions;
5) take one result from the course from informal statement to a
   sorry-free formal proof, and audit its axioms;
6) give a reasoned, referenced position on each item of the
   discussion agenda (Section V-D).

B. Phases

P01 runs in seven phases, 0 to 6, listed with topics, readings,
practice, and exit criteria in TABLE III
[file: 00_COURSE/tab/SP-00-T03_P01_PHASES.txt]. The order follows the
standard path through [3], [5], and [7].

The lectures themselves are set out in the syllabus, P01-SYL. The
phases are the backbone of the individual-exploration time; where
their order differs from the lectures, the lectures govern.

C. Session Cycle

Each session runs the PDCA cycle [15] shown in Fig. 2
[file: 00_COURSE/fig/SP-00-F02_SESSION_CYCLE.txt].

1) Before class (Plan, about 30 minutes): read the assigned material;
reread the actions in Section VII of the previous report; note which
open questions are likely to come up.

2) In class (Do): take raw notes; start the raw chat capture; do Lean
scratch work in the workspace.

3) After class (Check, within 24 hours, time-boxed to about two
hours): edit the chat log; write the report; carry out the critical
review.

4) Weekly (Act, about 30 minutes): update the best-practice,
open-question, and reference registers, and close completed actions.

5) End of each phase: write a phase review, Pnn-YYYY-MM-DD-PR, that
summarizes the phase and checks it against the exit criteria in
TABLE III.

D. Discussion Protocol and Agenda

Most class time is spent on what the material means. To keep those
discussions productive and recordable, each is written up in Section
V of the session report under the following protocol.

1) Question: state it in one sentence, precisely enough that it could
   turn out to be wrong.
2) Artifact: find the smallest Lean example that exhibits the issue,
   place it in the workspace, and cite it. A claim about Lean that
   cannot be shown in Lean is labeled as such.
3) Positions: record the positions taken, citing chat turns.
4) Lens: state the engineering analogy, using TABLE IV
   [file: 00_COURSE/tab/SP-00-T04_ENGINEERING_LENS.txt].
5) Breakdown: state where the analogy fails. This step is mandatory;
   an analogy without a stated limit is not accepted (BP-10).
6) Residue: what remains open goes to the open-question register in
   P01_LEAN/P01_INDEX.txt under an ID, P01-OQ-nn.

The opening agenda below seeds that register. Items are reopened as
the course reaches them. The artifacts are written in ASCII Lean
(TABLE II) and are to be checked in the editor during Phase 0 (A-03).

P01-OQ-01  What is a proof?
  In Lean, a proof of a proposition P is a term whose type is P, and
  checking a proof is type checking. Does this capture what a
  mathematician means by a proof, or only what a referee checks?
  Artifact:
    example (p q : Prop) (hp : p) (hq : q) : p /\ q := And.intro hp hq
  Start: [3, "Propositions and Proofs"], [9].

P01-OQ-02  What does a proof compute?
  Under propositions-as-types [8], [9], an implication is a function
  type, and a proof of p -> q is a function that turns evidence for p
  into evidence for q. Yet Lean erases proofs from compiled code. In
  what sense is a proof a program, and what is lost when it is
  erased?
  Artifact:
    example (p q : Prop) : p -> q -> p := fun hp _ => hp
  Start: [8], [9], [4].

P01-OQ-03  What, exactly, is trusted?
  When Lean reports "no goals", what has been trusted: the kernel, the
  axioms, the statement, the hardware it ran on? Compare the de Bruijn
  criterion -- a proof should be checkable by a program small enough
  to be reviewed by hand [11] -- with the traceability of a
  measurement to a primary reference standard.
  Artifact: #print axioms on a finished theorem. Compare a proof by
  decide with one by native_decide, which also trusts the compiler.
  Start: [2], [11], [12].

P01-OQ-04  Verified, but valid?
  Lean checks that a proof matches its statement. Nothing checks that
  the statement matches the intent. Natural-number subtraction in
  Lean truncates at zero, while fixed-width hardware wraps around:
  which one is "subtraction"? A theorem with an impossible hypothesis
  is true and useless.
  Artifacts:
    example : (2 : Nat) - 5 = 0 := by decide
    example : (2 : UInt8) - 5 = 253 := by decide
    example (x : Nat) (h : x < 0) : x = 42 :=
      absurd h (Nat.not_lt_zero x)
  Lens: verification versus validation [13].
  Start: [13], [5].

P01-OQ-05  Constructive or classical?
  Lean's core logic is constructive, but its axiom of choice yields
  the law of the excluded middle (Classical.em), and Mathlib uses
  classical reasoning freely. What is lost when a proof shows that
  something exists without showing how to build it? Compare a proof
  that some filter meeting a specification exists with a design
  procedure that produces one.
  Artifact: #print axioms Classical.em
  Start: [3, "Axioms and Computation"], [10].

P01-OQ-06  When are two things equal?
  Some equalities hold by definition and are closed by rfl; others
  hold only by proof. For n : Nat, n + 0 = n is definitional, but
  0 + n = n needs induction. Compare two identical netlists with two
  different netlists that a formal equivalence checker proves
  equivalent.
  Artifacts:
    example (n : Nat) : n + 0 = n := rfl
    example (n : Nat) : 0 + n = n := rfl            -- fails; try it
    example (n : Nat) : 0 + n = n := Nat.zero_add n
  Start: [3, "Quantifiers and Equality"], [7].

P01-OQ-07  Does an automated proof explain anything?
  Tactics such as simp, omega, and decide close goals without showing
  why. A proof is both a certificate that something is true and an
  explanation of why it is true. Which does Lean deliver, and which
  does a mathematician want? Compare synthesized or auto-routed
  hardware, which still goes to design review.
  Artifact: one lemma proved twice -- by omega, and by an explicit
  chain of rw steps.
  Start: [12], [5].

P01-OQ-08  Is mathematics being engineered?
  Mathlib [6] has naming conventions [19], continuous integration,
  deprecations, and refactors -- the apparatus of an engineered
  product. Does building mathematics as a maintained library change
  what mathematics is, or only how it is stored?
  Artifact: one Mathlib source file, read against [19].
  Start: [6], [19].

P01-OQ-09  What does the foundation change?
  Lean rests on dependent type theory, with a hierarchy of universes
  and a proof-irrelevant Prop, not on set theory. What is different
  about mathematics built on types rather than sets, and what stays
  the same?
  Artifacts:  #check Prop    #check Type    #check Type 1
  Start: [3, "Dependent Type Theory"], [10].

P01-OQ-10  What can formal proof not do?
  Incompleteness and undecidability bound every proof system, and a
  formal proof costs far more effort than an informal one [11]. The
  1994 Pentium FDIV flaw [20] is a standard example of a defect that
  testing missed, and Dijkstra observed that testing "can be used to
  show the presence of bugs, but never to show their absence" [21].
  Where does formal proof sit between testing and certainty?
  Start: [11], [12], [20], [21].

F. Research-Topic Protocol

A concept met in a lecture that deserves study of its own becomes a
research topic, RT-nn, entered in 00_COURSE/RESEARCH_TOPICS.txt. A
topic is opened by questions, not conclusions (BP-13; DEC-00, R-01).
Its opening note records the source and the claim, then the
assumptions in the source, then a set of opening questions, and only
then a preliminary analysis. The standard questions are listed in the
register. Work that would need long exploration is not pursued in the
session; it is entered in 00_COURSE/SIDE_PROJECTS.txt for the
author's decision (DEC-00, R-06, R-07).

The first topic, RT-01, was opened from lecture L01 [22] at 13:58, on
the claim that Lean moves syntax, runtime, and semantic errors alike
to the editor [P01-2026-11-25-RT01].

VI. CRITICAL REVIEW AND BEST-PRACTICE PROCEDURE
------------------------------------------------------------------------

A. Purpose

The last section of every report is its critical review. It is the
Check and Act steps of the PDCA cycle [15]: it judges the session's
work and notes, and it turns what was learned into practice for the
next session and the next project.

B. Review Questions

Section VII of each report answers, briefly and in this order:

1) What worked, in the studying and in the notes?
2) What did not work? What errors were found in this or earlier
   records? (Errata, cited by Document ID.)
3) What hidden assumption came to light -- in the mathematics, in
   Lean, or in the author's own reasoning?
4) Which best practices were applied (BP-nn), and what is the
   evidence?
5) Which prior work, internal or external, does this session
   confirm, extend, or contradict?
6) What new best practice, if any, is proposed?
7) What actions follow (A-nn), each with a due date?

C. Best-Practice Register

00_COURSE/BEST_PRACTICES.txt holds every practice the notebook
follows. Each entry gives an ID (BP-nn), a statement, its source (a
reference key or an internal record), the rationale, the records in
which it has been applied, and a status. The entries of this initial
issue, BP-01 to BP-12, are ACTIVE on adoption of this plan; BP-13 to
BP-17 were added by the declaration, DEC-00. Later
entries enter as PROPOSED from a critical review and become ACTIVE
once used in at least two sessions and judged worthwhile. A practice
that stops paying for itself is RETIRED, never deleted, and the
reason is stated. The register is kept at course level so that what
is learned in P01 carries into later projects.

D. Referencing Prior Work

The critical review cites its sources as the body does: external work
by [n], and earlier records in this notebook by Document ID. A lesson
that came from an earlier session is cited to that session, so the
reasoning behind every practice can be traced back to where it began.

VIII. CONCLUSION
------------------------------------------------------------------------

The plan fixes one form for every record: plain ASCII, IEEE-
structured, filed by project and by date, with tables and figures as
cited files and discussions as edited, cited chat logs. It puts the
weight of each session where the class puts it -- in discussion of

IX. CRITICAL REVIEW AND BEST PRACTICES INCORPORATED
------------------------------------------------------------------------

A. What Works

1) Traceability. Every claim, table, figure, and discussion point can
   be followed to a reference, a record, or a chat turn.
2) Grounding. The discussion protocol keeps the philosophical work,
   which is the bulk of class time, attached to checkable Lean
   artifacts.
3) Carry-over. The course-level registers let lessons from P01 serve
   later projects.
4) Durability. Plain ASCII at 72 columns can be read, printed,
   searched, and compared with standard tools for as long as the
   notebook is kept.

B. Weaknesses and Risks

1) Overhead. A full IEEE report and an edited chat log for every
   session may take longer than the time-box of Section V-C.
   Mitigation: the short form of Section IV; time measured over the
   first three sessions (A-05).
2) ASCII versus Lean. Lean and Mathlib are written in Unicode.
   Mitigation: .lean files are exempt, and notes use TABLE II.
   Residual risk: transcription errors between the two forms.
3) Editing drift. Correcting and tightening a chat log can shift its
   meaning. Mitigation: the RAW copy, verbatim code and quotations,
   and the [?] marker (Section III-F).
4) Unverified references. The references of this issue were compiled
   with an AI assistant and have not been checked against the
   sources; titles, page ranges, URLs, and the current revision of
