Abstract--The first concept taken from the lectures is a slide that
sorts the errors of scientific software into syntax, runtime, and
semantic, and claims that Lean catches all three in the editor. This
note opens the topic in the required order: the claim as made, the
assumptions on which it rests, the questions it raises, and only then
a preliminary analysis. The analysis finds the claim sound for
runtime errors by a specific mechanism, and conditional for semantic
errors: they are caught only against a stated theorem, which moves
the residual error into the specification.

Index Terms--software errors, static verification, specification,
type checking, floating point, Lean 4.

------------------------------------------------------------------------
I. SOURCE AND CLAIM
------------------------------------------------------------------------

The slide at 13:58 is transcribed and analyzed in Fig. 1
[file: fig/P01-2026-11-25-F01_L01_ERRORS_SLIDE.txt]. It lists three
categories of error, each with an example, the conventional
intervention (editor; running the program; human inspection and
testing), and the intervention in Lean, which is "Editor" for all
three.

The claim as spoken, from the automatic captions [1], which are not
verbatim:

    "what we're proposing is an approach to move all of these kinds
    of errors and catch them at the editor stage. This means we're
    going to ship code that is free of syntax, runtime, and semantic
    errors."

Three qualifications are spoken in the same chapter [1]:

1) A fourth category, floating-point and round-off error, is named
   and set aside: "That's not what we're focused on."
2) Asked whether the editor or the compiler gives the guarantee, the
   lecturer answers that the compiler technically does; the editor is
   where the author experiences it.
3) Asked whether a runtime error is also called a logic error, he
   answers "not necessarily", while noting that "we do use logic to
   prove that a program won't have any runtime errors."

The transcript carries no timestamps inside a chapter, so these
passages are cited to the chapter, and the slide to its second.

III. OPENING QUESTIONS
------------------------------------------------------------------------

Q1  Definition. By what criterion is an error put in a category: its
    cause, or the stage at which it is found? Is the list a
    partition, or do the categories overlap?

Q2  Mechanism, runtime. What in Lean turns an out-of-range index
    from an event at run time into an error in the editor?

Q3  Mechanism, semantic. Against what is a missing minus sign an
    error? What must the author supply before Lean can detect it?

Q4  Scope. What do the three "Editor" cells not cover? Candidates:
    floating point; an error in the specification; non-termination;
    exhaustion of stack or memory; the outside world reached through
    input and output; escape hatches in the language.

Q5  The student's question. Is a runtime error a logic error? Does
    the correspondence of proofs with programs (P01-OQ-02) give a
    sharper answer than "not necessarily"?

Q6  Lens. What is the nearest engineering practice, and where does
    the comparison fail?

Q7  Cost. What is paid to move detection to the editor, and when is
    the price worth paying?

Q8  Implication. If machines come to write both the code and the
    proof, what is left for the human to get right?

Q9  Refutation. What observation would show the claim to be false,
    or narrower than stated?

IV. PRELIMINARY ANALYSIS
------------------------------------------------------------------------

This section is the assistant's reasoning, offered for the author's
judgment. It is not yet the author's position.

A. On Q1: A Taxonomy of Stages

The slide's categories track where conventional practice finds the
error: in the editor, in a run, or by a person afterward. Read that
way, the claim is a re-staging: classes of defect found late are to
be found at the earliest stage. It does not say the causes vanish.

B. On Q2: Runtime Errors Become Proof Obligations

Lean's index notation carries an obligation: xs[i] is accepted only
with a proof that i is in range. The error is caught in the editor
because an unproved obligation is a type error. Lean also offers the
two conventional behaviors, under different notation, so the choice
is visible in the source text:

    #eval [10, 20, 30][2]     -- accepted: 2 < 3 is proved for you
    #eval [10, 20, 30][5]     -- rejected in the editor: no proof
    #eval [10, 20, 30][5]?    -- accepted: the result is "none"
    #eval [10, 20, 30][5]!    -- accepted: fails when run

The fourth line shows that the runtime row holds for code that
declines the escape hatch, not for all code that compiles.

C. On Q3: Semantic Errors Need a Stated Intent

A sign error is an error only relative to what was meant. Lean can
detect it only if what was meant is written as a statement:

    def f (x : Int) : Int := x - 1       -- intended: x + 1
    example : f 0 = 1 := by decide       -- rejected in the editor

Without the second line, the first is accepted. The "Editor" cell of
the Semantic row is therefore conditional on S4 and S5. The error is
not eliminated; it is relocated, from a long text (the program) into
a short one (the statement), where a person must still read it. This
is the distinction between verification and validation [2], and it
is P01-OQ-04.

D. On Q4 and Q9: What Stays Outside

1) Floating point (S1). A theorem about real numbers says nothing
   about the same formula evaluated in floating point.
2) The specification (S5).
3) Resources. A program proved correct can still exhaust the stack
   or memory; no type records that it will not.
4) Fixed-width integers. Arithmetic on a type such as UInt8 wraps
   without any error: a semantic error unless a theorem forbids it.
5) Unfinished or unchecked code: sorry, partial definitions, and
   code marked unsafe.

Any one of these, exhibited in a program that type-checks, narrows
the claim (Q9). Items 3 and 4 are the cleanest candidates to test.

E. On Q5: The Student's Question

Under the correspondence of proofs with programs, an out-of-range
index in checked Lean is a failure to supply a proof: a logic error
in the strict sense, found in the editor. In a conventional language
the same mistake is a false belief held by the programmer, which the
machine cannot inspect, and it surfaces at run time. One viewer's
comment under the video draws this line as "internal" against
"external" logic errors [1]. On this reading the lecturer's "not
necessarily" is right about conventional languages, and the sharper
answer for Lean is yes.

F. On Q6: Lens for the Reader of DEC-00, Section III-A

1) Closed-loop stability. Simulating step responses at chosen
   operating points is testing. A Routh-Hurwitz, Nyquist, or Lyapunov
   argument is a proof: it covers every initial condition in its
   domain. This is the difference between the conventional column
   and the Lean column.

   Where it breaks: the proof is about the model G(s), not the
   plant. Model error is specification error (item C). Control
   theory quantifies that gap with gain and phase margins. Lean has
   no margin: a statement is proved exactly or not at all.

2) Quantization. A filter designed as H(z) over the reals and built
   in fixed point has moved poles, round-off noise, and possibly
   limit cycles. The design proof does not carry to the
   implementation. This is the lecturer's excluded fourth category
   (S1), in the reader's own terms.

3) Units. Dimensional analysis rejects volts added to amperes with
   no theorem stated. Types do the same: a middle ground in which a
   class of semantic errors is caught without a full specification.

   Where it breaks: units catch a fixed class of mistakes; a type
   can state any property that can be proved.

G. Preliminary Position

The slide's claim holds in this form: for code inside the checked
part of the language, runtime errors of the indexing kind are
excluded by proof obligations, and semantic errors are excluded up to
the correctness of a formal statement that the author must write.
Floating point and resource limits are outside it.
